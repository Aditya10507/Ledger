## 1. Project Snapshot

**Name:** Ledger
**What it is:** An AI-powered reconciliation and anomaly-detection agent for the Razorpay AI Buildathon 2026 (AI Finance Controller track). It compares a merchant's transaction ledger against a bank/gateway settlement report, flags mismatches, explains each flag in plain English (grounded strictly in real computed data), and keeps a full audit trail of every decision.

**One-line pitch:** *"An AI Finance Controller that catches what your reconciliation spreadsheet can't — and shows its work."*

**Full detail lives in `/docs`:** `01_PRD.md`, `02_SRS.md`, `03_Architecture.md`, `04_UIUX_Plan.md`, `05_Development_Plan.md`. This file is the condensed, working reference — when in doubt about a detail this file doesn't cover, check the matching doc in `/docs` before guessing.

## 2. Non-Negotiable Rules (read this before writing any code)

These are guardrails. Do not deviate from them even if it seems like a shortcut:

1. **The AI (LLM) never decides whether something is an anomaly.** All matching and anomaly detection is deterministic, rule-based code (pandas/plain logic). The LLM's *only* job is to turn already-computed results into a plain-English explanation.
2. **Confidence scores are computed deterministically**, never generated by the LLM. Same input → same score, every time.
3. **The LLM prompt for explanations must only include pre-verified, computed data** (transaction IDs, amounts, deltas, timestamps, rule triggered). Never let it "reason freely" about whether a mismatch is real.
4. **The system never auto-resolves a financial discrepancy.** Every flag requires an explicit human decision (approve/reject/escalate).
5. **The audit log is append-only.** No update or delete route may ever exist for audit log entries — not even for admins.
6. **Every state change gets logged**: run creation, match computation, flag creation, every human decision.
7. **Don't build anything in the "Out of Scope" list (Section 6 below) unless explicitly asked.** Scope creep is the biggest risk to finishing this in time.
8. **If a file/data validation fails, fail loudly and specifically** — never silently drop rows or swallow errors.

## 3. Tech Stack (locked — don't swap without asking)

| Layer | Choice |
|---|---|
| Frontend | React + Tailwind CSS |
| Backend | Python + FastAPI |
| Reconciliation logic | pandas |
| Database | PostgreSQL (SQLite is fine for local dev) |
| AI | Claude API (Anthropic) — explanation generation only |
| Auth | JWT-based session tokens |
| Deployment | Docker + Render/Railway (backend), Vercel (frontend) |

No microservices, no message queue, no custom ML training, no GraphQL. Keep it simple — this is an MVP for a buildathon, not a scale-out system.

## 5. Data Model (condensed — see SRS Section 5 for full field list)

- **User** — id, name, email, password_hash, role (`analyst`/`admin`)
- **ReconciliationRun** — id, created_by, filenames, status, total/matched/flagged counts, flagged value
- **Transaction** — id, run_id, source (`ledger`/`settlement`), external_txn_id, amount, currency, timestamp, match_status
- **Flag** — id, run_id, flag_type, related_transaction_ids, computed_delta, confidence_score, ai_explanation, explanation_status, status (`open`/`approved`/`rejected`/`escalated`), reviewed_by, review_comment
- **AuditLogEntry** — id, entity_type, entity_id, action, actor, previous_state, new_state, timestamp

## 6. MVP Feature Scope

**Build (in this order — matches the Development Plan phases):**
1. Auth (login, JWT, role check)
2. CSV ingestion + validation (ledger + settlement files)
3. Reconciliation engine (txn ID match → amount/timestamp fallback match)
4. Anomaly detection: duplicate charge, missing settlement, amount mismatch, timing anomaly
5. AI explanation layer (grounded prompt, deterministic confidence score, graceful failure)
6. Review dashboard (Run Summary → Flag List → Flag Detail → Decision)
7. Audit trail (per-flag and global views)
8. Testing against seeded test cases, then deployment

**Explicitly out of scope — do not build unless asked:**
- Live bank/gateway API integrations
- Multi-currency / multi-tenant support
- Auto-resolution of discrepancies
- Email/Slack notifications
- Mobile app
- More than 2 roles (Analyst, Admin)
- Custom ML model training
- Historical trend analytics beyond one run-over-run summary

## 7. Anomaly Rules (defaults — keep these configurable, not hardcoded)

| Type | Trigger |
|---|---|
| Duplicate charge | Same amount + counterparty within 5 minutes |
| Missing settlement | No settlement record after 3 business days |
| Amount mismatch | Ledger vs. settlement amount differs by > ₹1 or > 0.5% (whichever is greater) |
| Timing anomaly | Settlement occurred outside expected settlement window |

## 8. Key API Endpoints

```
POST   /auth/login
POST   /reconciliation/runs                    # upload files, create run
GET    /reconciliation/runs                    # list runs (scoped by role)
GET    /reconciliation/runs/{id}                # run detail + summary
GET    /reconciliation/runs/{id}/flags          # list flags (paginated, filterable)
GET    /flags/{id}                              # flag detail
POST   /flags/{id}/decision                     # approve/reject/escalate + comment
GET    /flags/{id}/audit-trail
GET    /audit-log                               # admin only, global
```

## 9. Validation Rules (enforce these exactly)

- `amount` must be numeric, > 0
- `timestamp` must parse to a valid date/time
- `transaction_id` must be non-empty and unique within its source file
- `currency` must be consistent across all rows in a run
- File must have a recognizable header row (case-insensitive match ok)
- Any failure → specific, row-level error message. Never a silent drop, never a generic crash.
